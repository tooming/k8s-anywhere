# ADR-0029 amendment — cert-manager webhook-TLS follow-up's wave-ordering constraint

Docs-only finding, captured immediately after `auto/keda-engine` (#444) merged, while
scoping which of ADR-0029's two explicit follow-ups to pick up next.

## What was found

Started designing the "wire KEDA's admission webhook TLS to cert-manager's `k8s-lab-ca`"
follow-up (ADR-0029 §"Scope & exceptions"). The chart change itself looked like a
one-line `valuesObject` addition (`certificates.certManager.enabled: true` +
`issuer.generate: false` + `issuer.name: k8s-lab-ca`), but checking the chart's actual
template logic first (`templates/manager/deployment.yaml` +
`templates/manager/minimal-rbac.yaml`) surfaced a real problem: the cert volume's
`optional` flag is `{{ and .Values.certificates.autoGenerated (not .Values.certificates.certManager.enabled) }}`
— enabling `certManager` flips that volume from optional to **required**.

`keda` currently syncs at wave 1 (same wave as `cert-manager` itself). A required cert
volume means the operator/webhook pods can't start until KEDA's own `Certificate`
(created by its chart, referencing `k8s-lab-ca`) actually issues — but `k8s-lab-ca`
doesn't exist until `cert-manager-root-ca` reconciles at wave 5. Leaving `keda` at
wave 1 while making this change would be a **real circular deadlock**: ArgoCD's
sync-wave gating holds wave 4/5 until wave 1's `keda` Application reports Healthy, and
`keda` can't become Healthy without wave 5 having already run — not just a cold-start
delay, an actual stuck bootstrap.

This is exactly the kind of claim ADR-0004's "verify before asserting" discipline
exists to catch, extended to architecture research rather than dashboard content: it
would have been easy to write the one-line `valuesObject` diff, watch `make ci` pass
(clusterless — this sandbox can't exercise ArgoCD's live wave-gating at all), and ship
something that deadlocks the real bootstrap the first time a learner runs `make up`
from scratch.

## What shipped

Amended `docs/decisions/adr-0029-keda-event-driven-autoscaling.md`'s webhook-TLS
follow-up bullet with the finding and the fix it implies: move
`keda`/`keda-extras`/`keda-networkpolicy` to sync after wave 5 (wave 6, alongside
`lab-gateway-certificate`, which depends on the same `ClusterIssuer` for the same
reason) when that follow-up is actually built — a real re-plumbing of three
Applications' wave placement, not a one-line change, so it's captured here rather than
left for that PR to rediscover the hard way.

Deliberately **not** building the follow-up itself in this same pass: the wave-move is
real work deserving its own careful PR (re-verify every existing bats assertion that
hardcodes `keda`'s current wave, re-check nothing else assumes wave 1 placement) rather
than being rushed in alongside this finding.

## Verification

Docs-only change. `bash scripts/roadmap-check.sh` and `bash scripts/markdown-links-check.sh`
both pass. Full `make ci` green.
