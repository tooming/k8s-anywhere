# Bump KRO chart `0.4.1` → `0.9.x` — verify CRD/instance-scope compatibility first

CHARTER **Core Values** §"Everything as code" + general hardening; RFC #534 —
architect decision 2026-07-18. KRO's latest stable release is `v0.9.2` — five
minor versions ahead of this lab's `0.4.1` chart pin
(`gitops/platform/kro.yaml`). KRO is pre-1.0 (`0.x` semver — every minor
version is allowed to be breaking), and the `v0.9.0` release notes
specifically flag "cluster-scoped instance CRDs" — a change that may affect
the exact mechanism this lab depends on (the `ResourceGraphDefinition` in
`gitops/kro/rgd-s3bucketclaim.yaml` that generates the `S3BucketClaim` CRD
`gitops/platform/kro-resources.yaml` instantiates into the `ack-system`
namespace).

Per RFC #534's acceptance criteria the executor fetched the actual KRO CRD
definitions at the target tag and directly verified the instance-CRD scope
question before bumping. Closes #534.

## CRD/scope verification (per RFC #534's acceptance criteria)

Fetched `kubernetes-sigs/kro`'s (the project's current canonical org — the
`kro-run/kro` mirror used in earlier lookups resolves the same content) Go
API source at tag `v0.9.2`
(`api/v1alpha1/resourcegraphdefinition_types.go`) directly rather than
trusting the changelog wording: the `Scope` field on the RGD schema —

```go
Scope ResourceScope `json:"scope,omitempty"`
// Scope determines whether the generated instance CRD is Namespaced or
// Cluster scoped. Defaults to Namespaced to preserve existing behaviour.
```

— carries a `+kubebuilder:default="Namespaced"` marker. **The "cluster-scoped
instance CRDs" feature from the `v0.9.0` release notes is a new *opt-in*
field, not a change to the default.** `gitops/kro/rgd-s3bucketclaim.yaml`
never sets `spec.scope`, so the generated `S3BucketClaim` CRD stays
`Namespaced` after this bump — **no breaking change applies to this repo's
usage.** `gitops/platform/kro-resources.yaml`'s `destination.namespace:
ack-system` placement is unaffected.

## A real bug found while diffing `values.yaml` (per RFC #534's acceptance criteria)

Diffing the chart's `values.yaml` between `0.4.1` and `0.9.2` for every key
`gitops/platform/kro.yaml`'s `valuesObject` sets surfaced a pre-existing,
unrelated bug: the Application used `deployment.containerSecurityContext`,
but the chart's actual key — confirmed identical at both `0.4.1` and `0.9.2`
— is `deployment.securityContext`. `containerSecurityContext` has never been
a real path in this chart; the override has been silently dropped since this
Application was first written, so the KRO controller pod has never actually
received `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`,
or dropped capabilities. Same dead-key bug class as PR #493's Pyroscope fix
and the earlier ArgoCD/observability `podSecurityContext` key-mismatch fixes
this session's git history already shows.

**Fixed as part of this PR** (not a separate one — discovered directly by the
values.yaml diff this RFC's acceptance criteria already required): renamed
`containerSecurityContext` → `securityContext` in
`gitops/platform/kro.yaml`.

**Recurrence guard:** `tests/securitycontext-kro.bats`'s own header comment
already *claimed* "the KRO controller chart already ships with a hardened
securityContext... UID 65534, readOnlyRootFilesystem: true, capabilities.drop:
[ALL]" but had **zero assertions actually checking it** — only namespace PSA
labels and `kro-extras` wiring were tested, which is exactly why this dead key
went uncaught. Added five new assertions: the correct `securityContext` key
is present, the dead `containerSecurityContext` key is absent, and the three
specific fields (`allowPrivilegeEscalation`, `readOnlyRootFilesystem`,
`capabilities.drop: [ALL]`) are actually set — plus a chart-pin assertion.

## What changed

- `gitops/platform/kro.yaml`: `targetRevision` `0.4.1` → `0.9.2`;
  `deployment.containerSecurityContext` → `deployment.securityContext` (bug
  fix, see above). `podSecurityContext` (`runAsNonRoot`, `runAsUser: 65534`,
  `runAsGroup: 65534`, `fsGroup: 65534`, `seccompProfile.type: RuntimeDefault`)
  and `resources` unchanged — both keys verified unchanged at the new pin.
- `tests/securitycontext-kro.bats`: six new assertions (five for the
  securityContext fix, one for the chart pin).

## ADR-0004 caveat — what this run could NOT verify

This remote clusterless session cannot verify the KRO controller actually
starts cleanly at the new pin, nor that the `S3BucketClaim` instance
continues to reconcile against a live ACK S3 Bucket + moto backend, on a real
cluster. The `deployment.securityContext` key-name fix in particular has
never been exercised before — the field was previously a silent no-op — so
this is the first time these constraints (especially
`readOnlyRootFilesystem: true`) will actually apply to the running pod.

**Rollback path.** Revert both changes in `gitops/platform/kro.yaml` (the
chart pin and the securityContext key rename) together; ArgoCD self-heals.
Reverting only one (e.g. keeping the version bump but reverting the key name
back to the dead `containerSecurityContext`) would silently re-introduce the
same bug — always revert both in lockstep if a revert is needed.
