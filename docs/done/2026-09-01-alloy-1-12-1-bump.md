# Bump Grafana Alloy chart `1.11.1` → `1.12.1` (appVersion `v1.18.1` → `v1.19.2`)

(CHARTER **Core Values** §"Everything as code" + general hardening; upgrade-drafter fallback, executor.prompt.md STEP 6b — this run's thirteenth cycle: the "Now / next" lane remained fully gated and PLANNER found no ungroomed intake or un-RFC'd 🟡 item. Routine currency sweep re-checked Alloy, last reviewed 2026-08-20.)

Verified directly (not assumed, ADR-0004) via a real clone of `grafana/alloy` (the chart moved out of the old `grafana/helm-charts` monorepo into its own repo, `operations/helm/charts/alloy/`).

**Chart-level diff.** `git diff helm-chart/1.11.1 helm-chart/1.12.1 -- operations/helm/charts/alloy/` touches only `Chart.yaml` (`version: 1.11.1` → `1.12.1`, `appVersion: v1.18.1` → `v1.19.2`), `README.md`, and `CHANGELOG.md` — templates and `values.yaml` are byte-identical between the two versions. This means every schema fact this Application's own header comment previously verified across two prior bumps (no `--storage.path` volume, `global.podSecurityContext` not `controller.podSecurityContext`, `alloy.timeoutSeconds` as a flat key) still holds unchanged — no re-verification of those facts was needed, only confirmation the byte-identical claim itself is true.

**Binary-level breaking changes checked and ruled out.** The real top-level `CHANGELOG.md` for the `v1.18.1..v1.19.2` range names three breaking changes in `v1.19.0`: `prometheus.operator.servicemonitors` now rejects local-file TLS/bearer-token references by default; an OTel `memory_limiter` processor's internal telemetry metrics were renamed; and the `prometheus.write.queue` component was removed. Confirmed by direct grep of this lab's embedded River config: it uses none of `prometheus.operator.servicemonitors`, `memory_limiter`, or `prometheus.write.queue` — only `prometheus.remote_write`, `prometheus.scrape`, `discovery.kubernetes`, `discovery.relabel`, `loki.write`, `loki.source.kubernetes`, `pyroscope.write`, and `pyroscope.scrape`, none of which changed.

**Real, applicable fixes found:** a `discovery.relabel` fix ("use the underlying string of secret target values") — a component this config uses in four places (`pod_logs`, `node_exporter`, `envoy_proxy_pods`, `cilium_agent`) — plus several `loki.source.docker`/`loki.source.file` correctness fixes (not directly used here, but no regression risk since they're additive).

Bumped `gitops/platform/observability-alloy.yaml`'s `targetRevision: 1.11.1` → `1.12.1` and its header comment. Updated [ADR-0034](../decisions/adr-0034-lgtmp-observability-stack.md)'s table row and appended a new dated entry to its Re-evaluation log. Updated `docs/dependency-register.md`'s row.

**This Application is ALWAYS-ON** (automated sync) — this pin takes effect on the next ArgoCD reconciliation.

**ADR-0004 caveat.** This remote clusterless session cannot verify Alloy's pod actually restarts cleanly on the new chart version on a live cluster, or that every scrape/log/profile pipeline in the embedded River config keeps functioning against the new binary. Given the byte-identical template/values.yaml finding and the ruled-out breaking changes, risk is low, but a live-cluster session should confirm the "Lab — Grafana Alloy (Collector)" dashboard keeps populating post-bump. Rollback path: revert `targetRevision` back to `1.11.1`.
