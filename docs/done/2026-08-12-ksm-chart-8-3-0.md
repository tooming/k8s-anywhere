# Bump kube-state-metrics chart `8.2.0` → `8.3.0`

(CHARTER **Core Values** §"Everything as code" + general hardening; executor-fallback
currency sweep 2026-08-12, reached via `executor.prompt.md` STEP 6b UPGRADE-DRAFTER
role after Now/next's every remaining item was found gated (three Forgejo
migration items requiring live-cluster verification per their own item text; the
`verifyImages` Enforce flip and the O4 CI-rejection-gate item both blocked on
unconfirmed maintainer-confirmation issue #631, last comment 2026-08-11 13:09 UTC,
still not observed; the legacy capstone `Deployment` removal blocked on unconfirmed
issue #633, same last-comment timestamp) — no `docs/roadmap/incoming/` items and no
ungroomed open issues for the PLANNER role to act on, so this cycle escalated one
role further to UPGRADE-DRAFTER, whose lever (checking real upstream chart releases)
is genuinely time-varying rather than a repeat of an already-exhausted
repo-internal-consistency sweep.

Verified directly (not assumed, ADR-0004): a batch sweep of every Helm-chart
`targetRevision` under `gitops/platform/*.yaml` against its real upstream chart-source
git tags (`git ls-remote --tags`, since this remote session's egress policy does not
allow the Helm-repo index hosts themselves — `charts.jetstack.io`,
`prometheus-community.github.io`, etc. all returned 403 from the environment's
policy-enforcing proxy; `raw.githubusercontent.com` and `github.com` git-over-https
were both reachable and used instead) found every other pinned chart already at its
newest stable tag (cert-manager `1.21.1`, Cilium `1.18.12`, external-secrets `2.9.0`,
KEDA `2.20.2`, Kiali `2.30.0`, Kyverno `3.8.2`, Longhorn `1.11.3`, Alloy `1.11.1`,
Pyroscope `2.2.1`, Vault `0.34.0`, Velero `12.1.0`, TiDB Operator `1.6.6`, Harbor
`1.19.2`, Trivy Operator `0.35.0`, node-exporter `4.56.1`) except
**kube-state-metrics**, one minor release behind at `8.2.0` with `8.3.0` published on
`prometheus-community/helm-charts`.

`Chart.yaml`'s `appVersion` is unchanged (`2.19.1` → `2.19.1`) — same
packaging-only-bump shape as the prior `8.1.3` → `8.2.0` bump. A full diff of the two
tags' `values.yaml` (fetched per-file via `raw.githubusercontent.com`, since a full
`git clone`/`codeload.github.com` tarball fetch of this large monorepo was not
reachable through this session's proxy either) shows exactly one addition: a new
`rbac.customResourceState.createClusterRoleRules` key, defaulting to `true` — the
chart's existing implicit behavior. This repo's `valuesObject`
(`gitops/platform/observability-ksm.yaml`) sets no `rbac:` override at all, so the
new default applies and nothing changes. `templates/service.yaml`,
`templates/deployment.yaml`, `templates/clusterrole.yaml`, and `README.md` are
byte-identical between the two tags — the existing `securityContext`/
`containerSecurityContext` hardening and the `selfMonitor` `:8081` self-monitoring
port wiring (`tests/observability-ksm.bats`'s own regression-guard rationale) carry
forward unchanged.

Bumped `gitops/platform/observability-ksm.yaml`'s `targetRevision: 8.2.0` →
`8.3.0`. Updated `tests/securitycontext-observability.bats`'s exact-version-pin
assertion to `8.3.0` and added a new "does not pin the stale `8.2.0`" recurrence
guard (mirrors this repo's other version-pin test pairs — the `8.0.0`/`8.1.3` guards
already there). Updated `tests/observability-ksm.bats`'s header comment to note the
re-confirmation against `8.3.0`'s identical templates. Updated
[ADR-0034](../decisions/adr-0034-lgtmp-observability-stack.md)'s component table and
added a new dated `## Re-evaluation log` entry documenting the findings above.
Updated `docs/dependency-register.md`'s kube-state-metrics row "Last reviewed" cell.
No `docs/dependency-tree.md` update needed — it doesn't cite this chart's specific
version (checked directly, only descriptive "KSM" prose).

`make ci` must pass. PR body documents the ADR-0004 caveat that this remote
clusterless session cannot verify the operator reconciles cleanly and continues
exposing metrics post-bump on a live cluster — rollback path: revert
`targetRevision` to `8.2.0`; ArgoCD re-syncs the prior chart version on next
reconciliation; kube-state-metrics is stateless (no PVC), so a rollback recovers
immediately with no data loss.
