# Bump Kargo Helm chart `1.10.9` → `1.11.0`

CHARTER **Core Values** §"Everything as code" + general dependency hygiene.
Upgrade-drafter fallback sweep (`executor.prompt.md` STEP 6b) after the
"Now / next" lane again came up fully gated on the standing
maintainer-confirmation issues #631/#632/#633 (re-checked this cycle — still
zero comments on any of the three, `updated_at` unchanged since
2026-07-21T05:34 UTC), and both the planner and architect fallbacks found
nothing to do (no open GitHub issues to groom beyond the three standing
trackers, `docs/roadmap/incoming/` empty, and every 🟡 item in ROADMAP.md's
hardening section is either already RFC'd/decided or struck through).

- Component: `kargo` Helm chart, OCI registry `ghcr.io/akuity/kargo-charts`
  (`gitops/platform/kargo.yaml`, ADR-0023). Kargo is ON-DEMAND (no
  `automated:` sync block), so this pin only takes effect on the next
  `make kargo-up` — zero live-cluster blast radius either way.
- From → To: chart `1.10.9` → `1.11.0`. Not a major bump (`1.x` line).
- Why this version: confirmed `1.11.0` is a real, non-pre-release tag via the
  OCI registry's own tag list
  (`ghcr.io/v2/akuity/kargo-charts/kargo/tags/list?n=1000` — the default
  unpaginated response silently truncates to old tags, a real footgun caught
  while checking). No newer stable tag exists beyond `1.11.0` (only
  `1.11.1-rc.*`/`1.11.2-rc.*` pre-releases).
- **Schema/compatibility verification (ADR-0004):** the OCI blob CDN itself is
  proxy-blocked in this sandbox (same restriction noted in prior sweeps for
  `*.github.io`/`public.ecr.aws`), so compatibility was verified against the
  equivalent real source instead — the chart's committed `charts/kargo/
  values.yaml` fetched live at both git tags via `raw.githubusercontent.com`
  (`akuity/kargo/{v1.10.9,v1.11.0}/charts/kargo/values.yaml`). Diffed both
  files directly: every value path this Application sets
  (`global.securityContext`, `api.{replicas,resources,tls.selfSignedCert,
  secret}`, `controller.{replicas,resources}`, `webhooksServer.{replicas,
  resources}`) is present, unchanged, at both tags. The entire diff is
  additive — new optional Dex BYO-OIDC proxy config, `revisionHistoryLimit`/
  `rollingUpdate` tuning knobs, and coarse `workloads`/`dataPlane`/`argocd.
  dataPlane` install switches that all default to the prior (implicit)
  behavior — plus parameter-doc comment rewording. No key this repo
  references was renamed, removed, or restructured.
- Also independently checked the release's own cited breaking-changes list
  (via a web fetch of the GitHub release notes, treated as lower-confidence
  per ADR-0004 since the summarizing step could not be cross-verified against
  a second source): the two Helm-chart-facing items it named
  (`rbac.useDefaultServiceAccount` removal, `allowTags`/`ignoreTags`
  deprecated-field enforcement) — a repo-wide grep confirms neither key is
  referenced anywhere in `gitops/`, so neither applies to this lab regardless
  of whether that summary was fully accurate.
- No CVE is cited against `1.10.9`, and none is fixed specifically by
  `1.11.0` — this is routine version currency, not a security-driven bump
  (unlike the two prior CVE-driven Kargo bumps recorded in `gitops/platform/
  kargo.yaml`'s own header comment: `1.2.3`→`1.6.4`, `1.6.4`→`1.10.9`).
- Updated `docs/decisions/adr-0023-kargo-promotion-pipeline.md`: corrected the
  stale "Chart + version" block (it still said Helm repo `https://
  charts.kargo.io` / version `1.2.0`, six bumps out of date — the repo URL
  was fixed to the OCI registry and the version field now points at the
  Re-evaluation log instead of duplicating a number that will drift again),
  and added a new dated Re-evaluation log entry for this bump.
- Updated `tests/kargo.bats`: the chart-pin assertion now checks for
  `1.11.0` and the "does not pin an old version" assertion now also excludes
  `1.10.9` (previously only excluded `1.6.4`/`1.2.3`).
- `make ci` green (locally: lint/drift/dependency-tree/ADR-sync checks all
  pass; kubeconform/kustomize/terraform/bats/helm-chart-pin-check aren't
  installed in this remote sandbox and run for real in GitHub Actions, same
  as every other PR from this environment).
