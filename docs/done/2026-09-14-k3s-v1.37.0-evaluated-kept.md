# k3s v1.37.0 evaluated, deliberately kept at v1.36.4+k3s1

## What

`k3s-io/k3s` shipped `v1.37.0+k3s1` on 2026-09-14 (today) — the first
stable release on the `1.37.x` minor line (the prior five tags,
`v1.37.0-rc1` through `-rc5`, were pre-releases only, published between
2026-09-02 and 2026-09-11). This repo's k3s pin (ADR-0030) is at
`v1.36.4+k3s1` on both backends.

## Why this is not a routine bump

Every prior k3s bump this ADR's Re-evaluation log records was a **patch**-
line move (`v1.36.2` → `v1.36.3` → `v1.36.4`). `v1.37.0` is a Kubernetes
**minor**-line jump. ADR-0030's own Scope & exceptions section already
draws this distinction: "future k3s bumps go through the architect's
CVE-sweep + RFC path... not a routine drive-by version bump" — and this
run's own established convention elsewhere (e.g. Grafana's `13.0.x` →
`13.1.x` handling) treats a version-line jump as needing deeper diligence
before adoption, not a same-shape edit to a routine patch bump.

## Verification

- `github.com/k3s-io/k3s/releases` — confirmed `v1.37.0+k3s1` is the newest
  stable tag, published 2026-09-14 (today), Kubernetes `v1.37.0` under the
  hood.
- `github.com/k3s-io/k3s/releases/tag/v1.37.0+k3s1` — read the release's own
  notes directly: the stated primary focus is **CVE-2026-84445** (gRPC-Go
  xDS servers: DoS via crash on a request missing both `:authority` and
  `Host` headers), fixed by bumping `google.golang.org/grpc` to `v1.83.2`.
- Read the CVE-2026-84445 advisory directly: the vulnerable code path
  requires a server built with `xds.NewGRPCServer()` — gRPC's xDS
  control-plane server mode (used by service-mesh/xDS management-plane
  components like Istio's control plane). k3s's own gRPC usage
  (containerd's CRI socket, k3s's internal supervisor/agent protocol)
  does not construct an xDS server this way — **this CVE does not apply
  to this lab's actual k3s deployment**, the same "is the vulnerable code
  path actually exercised" diligence already applied to every Traefik/
  ArgoCD GHSA sweep this run.
- Live web search cross-checked against multiple independent sources: the
  underlying Kubernetes `v1.37.0` release carries real, documented breaking
  changes not called out in k3s's own (narrower) release notes — static
  pods may no longer reference `Secret`s/`ConfigMap`s, the kubelet refuses
  to start when a deprecated cAdvisor flag is set (18 kubelet flags dropped
  total), `SELinuxMount` graduates to GA and flips **on by default**,
  kubeadm drops the `v1beta3` config API, a batch of metrics are removed,
  and kube-proxy begins its move from iptables to nftables.
- Community guidance (multiple independent sources) is explicit: treat a
  `.0` release as the least production-exercised state of a new line and
  wait for `v1.37.1`/`v1.37.2` — ordinary, conservative version-adoption
  practice.

## Decision: Keep at `v1.36.4+k3s1`

The one named security fix in `v1.37.0` doesn't apply to this lab; the
underlying Kubernetes minor line's documented breaking changes are real
and unverifiable against a live cluster from this remote, clusterless
session (ADR-0004 — no live cluster to prove `make up` still bootstraps
cleanly under the new kubelet-flag and `SELinuxMount` defaults); and
general practice is to let a `.0` release mature. Bumping now would trade
an unverified regression risk for a security fix that doesn't apply here.

## Fix

No code/config change — this is a documented evaluate-and-decide entry,
the same "Decision: Keep" shape ADR-0030's own Re-evaluation log already
uses (see its 2026-07-28 entry for precedent). Updated:

- `docs/decisions/adr-0030-pin-k3s-version-explicitly.md`: new
  2026-09-14 Re-evaluation log entry with the full reasoning and a new
  flip condition (`v1.37.1+` ships, past the day-of-`.0` caution window).
- `docs/dependency-register.md`: k3s row's dated entry updated to match
  (enforced by `dependency-register-sync-hook.sh`).
- `ROADMAP.md`: Cross-cutting hardening entry recording this cycle's
  diligence pass as done work — no separate backlog item needed since
  the ADR's own flip condition is this repo's established tracking
  mechanism for "recheck later" dependency findings (same shape as
  Traefik's "re-check when the k3s pin next bumps" note).
