# Bump Valkey image pin `8.1.9-alpine` → `8.1.10-alpine` — SECURITY release (GHSA-jcj7-v34w-v9vv), ADR-0018's own flip condition triggered

(CHARTER **Core Values** §"Real observability only" / general hardening + ADR-0004; planner-fallback gap analysis 2026-09-01, reached via `executor.prompt.md` STEP 6b after the "Now / next" lane was re-confirmed fully gated this cycle — the two standing GitLab→Forgejo migration items and the capstone-`Deployment`-removal item all remain blocked on the same unconfirmed live-cluster/design prerequisites (issues #633/#1229/#1345 all still open, latest comments unchanged since 2026-08-25), and no un-RFC'd 🟡 item or ungroomed intake issue exists. Fresh angle this cycle: re-check every plain `image:` pin for a newer upstream release rather than assume the 2026-08-17 sweep's findings still hold three weeks later.)

Verified directly (not assumed, ADR-0004): fetched `github.com/valkey-io/valkey/releases/tag/8.1.10` and `raw.githubusercontent.com/valkey-io/valkey/8.1.10/00-RELEASENOTES` directly — published 2026-08-31, "Upgrade urgency SECURITY: This release includes security fixes we recommend you apply as soon as possible", documenting `GHSA-jcj7-v34w-v9vv` (a use-after-free in RDMA connection handling allowing an authenticated client to crash the server via `CLIENT KILL`; only affects builds compiled with `USE_RDMA` and an RDMA listener configured — this lab's stock `valkey/valkey:8.1.9-alpine` image is not RDMA-enabled, so this specific CVE doesn't reach it as deployed) plus several unconditional bug fixes on the same tag: AOF recovery of a truncated MULTI/EXEC block that could lose writes after a restart, listpack validation on RDB load/RESTORE to prevent deferred crashes, and multiple use-after-free fixes in TLS handling, cluster messaging, and stream processing. This is exactly the flip condition [ADR-0018](../decisions/adr-0018-valkey-not-redis.md)'s 2026-08-17 re-evaluation log entry names verbatim: *"A CVE or critical-bug advisory is disclosed against the `8.1.x` line (from `8.1.9` onward) that a later patch fixes ... bump the pins to the fixed/needed version and add a new dated log entry here."* No `8.1.11`+ tag exists (checked the same releases page) and no major-version jump is involved — smallest safe delta.

**Groundedness check before implementing (ADR-0004).** The GitHub source tag existing is not sufficient — also verified the built Docker image itself. A direct `GET https://hub.docker.com/v2/repositories/valkey/valkey/tags/8.1.10-alpine` initially returned **HTTP 404** on 2026-09-01 (checked twice, minutes apart, in an earlier cycle of this same run) even though the identical query for `8.1.9-alpine` correctly returned real tag data — the multi-arch image build had not yet caught up to the GitHub source tag (mirrors this repo's established "not yet groundable" precedent, e.g. Velero `v1.18.2` in the 2026-08-25 industry digest). Rather than fabricate immediacy, the prior cycle's `plan/*` PR (#1360) recorded this honestly and gated implementation on a fresh re-check. Re-checked in this cycle: the image is now published (`valkey/valkey:8.1.10-alpine`, multi-arch amd64/arm64/ppc64le/armv7, `last_updated: 2026-09-01`, uploaded by `valkeybot`) — confirmed before making any manifest change.

Bumped `gitops/data/valkey/statefulset.yaml` and `gitops/data/demo/valkey-load.yaml`'s `image: valkey/valkey:8.1.9-alpine` → `image: valkey/valkey:8.1.10-alpine` (both moved together, matching ADR-0018's own prior-bump precedent). Updated `statefulset.yaml`'s existing header comment block to describe this bump: the SECURITY-release finding, the RDMA-inapplicability note, the other unconditional bug fixes, and the Docker Hub groundedness check. Updated `tests/data-layer.bats`'s two pin assertions (retitled to name the GHSA ID) plus their negative assertions to confirm the superseded `8.1.9-alpine` tag is gone from both files. Added a new dated entry to [ADR-0018](../decisions/adr-0018-valkey-not-redis.md)'s `## Re-evaluation log` documenting the flip (prior entries kept, not deleted) and a new flip condition. Updated `docs/dependency-register.md`'s Valkey row "Last reviewed" cell to cite this bump.

**ADR-0004 caveat.** This remote clusterless session cannot verify the Valkey pod restarts cleanly and the "Lab — Valkey" dashboard keeps populating post-bump on a live cluster. Rollback path: revert both `image:` tags back to `valkey/valkey:8.1.9-alpine`; Valkey is a plain `StatefulSet`, not an ArgoCD-templated Helm release, so a revert takes effect on the next GitOps sync. The AOF-off/RDB-snapshot-every-60s config means at most 60s of writes could be lost on an actual server crash during the window, unrelated to this image-tag change itself.
